# Archaeology V3 offline preview (FLARE-FINAL-001)

This is a **Node.js offline, read-only** validation contract. It does not add a website entry point, invoke the existing importer, merge records, write IndexedDB/Firebase, or produce an importable bundle. Ordinary V1/V2 and PR #132 are unchanged.

## Input boundaries

Call `preview({originals, review, candidate})`. Originals are independently obtained original bytes as `[{sha256, bytes: Buffer}]`, including the original baseline of any prefix join. SHA-256 is recomputed before parsing; strict UTF-8 and BOM handling preserve original byte identity. Do not stringify the parsed original to reproduce its hash.

The **trusted operator** supplies `review` from independent examination, separate from the archaeologist's candidate. `review.sources` is an ordered list of approved display sources `{sha256, chatId, runId, status, count, reviewId}`; the count for a prefix join is the full candidate count, not the local prefix count. Baseline bytes must also be supplied in originals, but need not be an independent display source. A separate continuation keeps its own chatId, source index and hash. Source order is explicit, not guessed from dates. Repeated chatId among display sources is refused; overlapping snapshots of one chat require separate reconciliation first.

`review.targets` contains authorized worldKey, cycleId and cycleTitle triples. The unique target identity is the exact pair (worldKey, cycleId), in both review and candidate; cycleTitle must separately equal the reviewed title. Duplicate pairs are rejected even when titles differ. The review keys retain the full triple to bind approvals to the reviewed title; cross-cycle conflict detection and missing target reports use the identity pair. `review.fragments` contains `{key, reviewId, reason}`, where key is generated by the exported reviewKey(target, manager, section, ref, fragment, context). This registry must be created from independent review, not copied from the candidate, and is not cryptographic proof that the reviewer did their work. No automatic semantic certification is claimed.

## Candidate

`{format:"gal-predecessor-archaeology-preview",version:3,manager,targets:[{target,pilotMessages,quizLogs,casinoLogs,realChatLogs,rejectedEvents,easterEggs}]}`. Each section is an explicit array, possibly empty. Each entry references one source using `{sha256,chatId,sourceId,sourceIndex,fragments:[{start,end,text,kind}]}`. All offsets are JS UTF-16 code units, half-open. Exact original slice, nonempty text, no surrogate-pair cuts, no overlap/reordering, no duplicate source per target/section. One source retains one stable display identity; fragments remain independent, never joined into a fake original text. Repeated identical phrases are disambiguated by offset. Sections can legitimately overlap in meaning.

Player commentary before the first story marker is allowed as in V2, with context prefix. In all six sections, user commentary, player-correction and player-annotation may not cross a marker. Post-marker commentary requires independent review with context reviewed-outside-story. Player corrections/annotations in any section require the original user role, a preceding player block or prefix, and explicit independent review scoped to exact source, range, target, manager, section, kind and actual block. Gal AI output and assistant rows cannot be marked as player corrections/annotations, even with an approval. Moving a fragment to another section cannot bypass these rules. Existing pilot-specific limits remain. Evidence-only kinds may quote story text outside the pilot player restriction without asserting player authorship; they still require independent semantic review before production. Marker matching is a conservative structural aid, not a semantic parser; ambiguous cases remain outside approved entries. Reviewers must exclude story prose masquerading as commentary even if a marker is missing. Rebuild affected non-pilot user commentary/annotation/correction coverage and review keys from independent review; do not silently promote old context source keys.

Rejected events include decision `{sha256,chatId,sourceId,sourceIndex,start,end,text}`; the decision must be a user span outside Gal AI output and may not cross a marker; the exact event body (all ordered fragments), optional title, player decision and relation require an independent review entry keyed by exported entryReviewKey(target,manager,'rejectedEvents',entry). Replacing any evidence invalidates the approval. The preview does not promote events to canon. Easter eggs include title and confirmed/uncertain plus exact raw evidence fragments, all bound by entryReviewKey(target,manager,'easterEggs',entry). Both statuses need independent approval; changing uncertain to confirmed requires a new approval. No automatic truth claim.

## FLARE-FINAL-002: cross-cycle and full coverage

Same or overlapping ranges of the same original row across distinct target cycles (including across sections and decision references) are rejected as a placement conflict unless the independent operator supplies the exact pair in review.crossCycle as {key,reviewId,reason}. Generate the pair key using crossCycleKey(manager,coverageKeyA,coverageKeyB), with decisionCoverageKey for a decision reference. This does not prohibit ordinary cross-tab classification within the same cycle or separate nonoverlapping ranges of one source being assigned to different cycles. It does not infer cross-cycle permission from a title or shared manager.

For final coverage call preview with requireFullCoverage:true, independently of candidate flags. Supply review.coverage, exactly one entry per row of every approved display source: {sha256,chatId,sourceId,sourceIndex,disposition,keys,reviewId,reason}. Disposition is selected, excluded or isolated. Selected rows have nonempty exact keys; excluded and isolated rows have empty keys plus a reason. Unresolved composites can only be isolated. Build each expected key from independent final review using coverageKey(target,manager,section,entry,fragment,context); context follows the structural rule in this contract. A rejected event decision also needs its own decisionCoverageKey(target,manager,entry) in the decision source row's coverage. Event and egg keys bind all associated evidence and semantic metadata. Do not generate the expected ledger from the submitted candidate. Full mode reports missing source rows, missing and unexpected fragments, omitted authorized targets, unused semantic approvals and unused cross-cycle approvals. If any exist, coverage.status is incomplete; only complete-against-independent-ledger indicates full agreement. Without full mode, coverage.status is not-requested, never certified. The trusted review and source list must themselves be independently established; no program proves their historical truth. None of these outcomes authorizes import.

## Source rules

Completed display must have topReached/bottomReached/continuity true. Observed-prefix source retains its original status, openingVerified=false and warning true-opening-unverified. The actual base bytes must match the embedded base SHA, chatId, runId, count and first ID. Validate local/candidate/base rows, ordered overlap of at least two by the current scanner compareRow on index-free rows, and reconstruct candidate exactly from local prefix + base. No arbitrary fold normalization, no status changes or permissive offline-candidate wrapper. Any mismatch is an unresolved blocker, not grounds to relax the validator. No server manifest is implied. Unresolved composite rows remain counted as isolated but cannot be selected.

## Output

Preview-only, canonical=false, importable=false. Each fragment has exact original offsets/text and context, each source retains its provenance and warning. Source totals count display units, entry totals count target/section groups (not distinct source turns), fragment totals count excerpts. Full coverage is a set comparison against a separately supplied independent ledger, not a claim of true historical completeness or an automatic semantic review. It does not preserve a production renderer's image metadata or implement revision writes, old-data migration, backups, rollback, ordering across existing website entries, or production storage. Those are separate gated tasks.
